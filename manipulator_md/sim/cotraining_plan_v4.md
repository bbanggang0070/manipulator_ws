# co-training v4 학습 계획 — sim(v4_200) + 실기(real_v2)

> sim-only 모델의 실기 zero-shot이 실패한 것을 확인하고, 실기 도메인 적응을 위해
> sim + 실기를 혼합 학습한다.
>
> 작성 2026-08-10 · 관련: [보고서](README.md) · [데이터셋 카탈로그](datasets.md)

---

## 1. 근거 — zero-shot은 왜 실패했나

`gr00t_blocktask_v4_200_n16_8bit/checkpoint-86000`(sim 75.6%)을 실기에 그대로 붙였다.

| | 관측 |
|---|---|
| 서버 | 정상 응답 (infer 65~75ms) |
| 클라이언트 | 정상 실행 (1,131 청크 / 9,057 액션 기록) |
| **로봇** | **초반 1회 크게 이동 후 정지** |

```
시작       pan   3.34  lift −92.57  elbow  95.78   ← 홈
   ↓ (초반 10%에서 lift 113°, elbow 110° 이동)
이후       pan −24.62  lift   3.69  elbow −13.32   ← 여기서 고착
현재       pan −24.62  lift   3.78  elbow −13.32   (최근 100청크 이동량 0.00°)
```

**고장이 아니라 정책이 한 자세로 수렴(collapse)한 것**이다. 실기 이미지가 학습 분포 밖이라
어떤 상태에서도 같은 액션을 내보내고, 그 자세에서 본 이미지가 더 OOD가 되어 고착이 강화된다.

> **sim 성능이 실기로 그대로 옮겨지지 않는다는 것이 실측으로 확인됐다.**
> sim 75.6%는 co-training의 **출발점 품질**이지 실기 성능의 예측치가 아니다.
> 선례도 같다 — sim-only v2는 실기 10%였고 co-training으로 90%가 됐다.

## 2. 데이터 구성

| | 데이터셋 | ep | frames | 비고 |
|---|---|---|---|---|
| sim | `sim_so101_blocktask_v4_200` | 200 | 82,951 | 근접 54.5% 보강본 |
| 실기 | `so101_blocktask_real_v2` | **57** | **38,362** | 박스 다양성 확보, ep2·33·49 제외 |

### 실기 데이터 품질 점검 결과

| 지표 | 값 | 판정 |
|---|---|---|
| 길이 | 평균 693 f (23초), 범위 413~1354 | 정상 |
| 시작 idle | 평균 20 f (0.7초), 최대 50 | 정상 |
| 종료 idle | 평균 35 f (1.2초), 최대 69 | 정상 |
| 그리퍼 변화폭 | 최소 13.7 | **전 ep 파지-해제 수행** ✅ |
| NaN | 0 | ✅ |
| 액션 최대 점프 | 6.9° | 불연속 없음 |
| 추종 오차 \|action−state\| | 평균 1.48° | 팔로워 추종 양호 |

**재시도 검출**: 그리퍼 개폐 전이 횟수로 판별했다. 55ep이 3회(정상 1사이클)인데
**5ep만 5회**로 튄다 — `ep2, ep33, ep38, ep47, ep49`. 길이 이상치(ep33·ep47)만으로는
못 잡던 것을 이 지표가 3개 더 찾아냈다.

영상 확인 결과 **`ep2` · `ep33` · `ep49` 제외**(재시도 섞임), `ep38` · `ep47`은 유지.
→ **57ep / 38,362 frames** (제외분 3,192 f)

> 길이만 보면 ep47(1217 f)이 ep2(789 f)보다 훨씬 긴데 ep2가 제외됐다.
> **길이는 재시도의 신뢰할 만한 지표가 아니고**, 그리퍼 사이클이 직접적이다.

### 기존 `real50`을 쓰지 않는 이유

| | |
|---|---|
| **박스 고정** | 50ep 전체에서 박스 픽셀 중심 편차 x 7px, y 4px. 배포에서 박스를 옮길 것이므로 다양성이 0인 채로 배우게 된다 |
| **카메라 구도 불일치** | 카메라를 sim v4 구도로 재정렬하며 era90 대비 **세로 약 114px 이동**. 섞으면 배포에 없는 구도를 함께 배운다 |

## 3. 스텝 산정

`mix_ratio`는 **샘플링 가중치**다. sim 1.0 / 실기 1.0이면 데이터 크기와 무관하게 **50:50으로 뽑는다**
(`launch_cotrain.py`). 따라서 각 데이터셋의 epoch은 `steps × 64 ÷ 2 ÷ frames`로 계산된다.

**선례**(sim_v2 30,887f + real50 21,175f, 20k → 실기 90%): sim **20.7** epoch, 실기 **30.2** epoch.

| steps | sim epoch | 실기 epoch | 시간 | |
|---|---|---|---|---|
| 36,000 | 13.9 | **30.0** | 27h | 선례의 **실기** epoch 일치 |
| 43,000 | 16.6 | 35.9 | 32h | |
| **48,000** | **18.5** | **40.0** | **36h** | **기본안** |
| 54,000 | 20.8 | 45.0 | 41h | 선례의 **sim** epoch 일치 |
| 86,000 | 33.2 | 71.7 | 65h | 과할 가능성 |

### 기본안: **48k** (약 36시간)

- 선례의 sim epoch(20.7)과 실기 epoch(30.2) **사이**에 놓인다(sim 18.5 / 실기 40.0).
- 데이터가 2배 이상 커졌으므로 절대 스텝을 20k로 두면 학습량이 절반 이하가 된다.
- 86k까지 갈 근거가 없다 — co-training은 sim으로 표현을 익히는 단계가 아니라
  **실기 도메인에 적응시키는 단계**이고, 선례가 20k로 90%를 냈다.

> **스텝을 정확히 맞출 필요는 없다.** co-training의 목표 지표는 sim SR이 아니라 **실기 SR**이고,
> 그건 체크포인트마다 측정할 수 있다. `--save-steps 5000`으로 저장하고
> **중간 체크포인트를 실기에서 평가**해 최적 지점을 고르는 편이 낫다(§5).

## 4. 하이퍼파라미터

**v4_200 학습과 전부 동일**하게 둔다 — 변수를 '실기 데이터 혼합' 하나로 유지하기 위함이다.

| 항목 | 값 |
|---|---|
| base model | `nvidia/GR00T-N1.6-3B` (v4_200 체크포인트가 **아님**) |
| learning rate | 1e-4, cosine, warmup 0.05 |
| weight decay | 1e-5 |
| micro batch × grad accum | 2 × 32 = **64** |
| optimizer | `paged_adamw_8bit` |
| 증강 | color jitter (b0.3 c0.4 s0.5 h0.08) |
| dataloader workers | 8 |
| **max steps** | **48,000** |
| **실기 mix_ratio** | **1.0** |

> **왜 v4_200에서 이어받지 않고 base부터인가**: 선례가 그렇게 해서 90%를 냈고,
> sim 가중치에서 출발하면 실기 적응이 sim 표현에 끌려간다. 또 [training_plan §2](training_plan.md)의
> resume 위험(cosine LR 완주, 샘플러 상태, forgetting)이 그대로 적용된다.
> 다만 **sim 스킬을 처음부터 다시 배워야 하므로** sim epoch이 18.5로 v4_200(66.3)보다 훨씬 적다 —
> 이것이 근접 스킬 유지에 충분한지는 §5의 실기 평가로 확인한다.

## 5. 실행과 평가

```bash
# 5090 — 서빙 중이면 먼저 내린다(VRAM)
~/serve_blocktask_n16_5090.sh '' stop
~/train_gr00t_blocktask_cotrain_v4_n16_8bit.sh "" 1.0 48000
```

### 평가 — 실기에서, 체크포인트별로

sim SR은 참고치일 뿐이고 **판정은 실기 SR**로 한다.

| 시점 | 할 일 |
|---|---|
| 20k, 30k, 40k, 48k | 각 체크포인트를 서빙해 **실기 10회** 측정 |
| 각 회차 | `LOGDIR`로 시행별 분리 저장(rerun 실시간 + `video.mp4` + `actions.csv`) |

```bash
# 5090
~/serve_blocktask_n16_5090.sh gr00t_blocktask_cotrain_v4_n16_8bit/checkpoint-30000 start
# 로컬
cd ~/manipulator_ws/setup/gr00t
LOGDIR=~/manipulator_ws/logs/cotrain_v4/ck30000_trial01 \
STEP_DT=0.033 SERVER_HOST=192.168.0.56 ENSEMBLE=1 ENSEMBLE_W=0.3 ./home_then_infer.sh
```

> **홈 자세 주의**: 실기 데이터로 co-train한 모델은 `HOME_SCRIPT=goto_home_real.py`가 맞다
> (실기 rest 자세, elbow +89.8 → 초반 rest 지연 제거). sim-only 모델용 `goto_home_sim.py`와 다르다.

### 판정 기준

| 지표 | 목표 | 근거 |
|---|---|---|
| **실기 SR** | **≥ 80%** | 선례 co-training 90% |
| 정지(collapse) 발생 | **0회** | zero-shot의 주 실패 형태 |
| 박스 위치 변화 대응 | 성공 | real_v2로 보강한 축 |

### 실패 시 조정 순서 (싼 것부터)

1. **다른 체크포인트** — 20k~48k 중 최적 지점이 다를 수 있다 (추가 학습 0)
2. **`ENSEMBLE_W` 조정** — 과거 0.5~2.0 실험에서 큰 개선은 없었으나 확인 비용이 0
3. **실기 mix_ratio ↑ (1.5~2.0)** — 실기 적응이 부족하면. 재학습 36h
4. **실기 데이터 추가 수집** — 위로 안 되면. 배치표는 이미 있다(±45°로 좁혀서)

## 6. 남은 한계 (기록)

- **sim에서 발견한 병목이 미해결**: 블록이 오른쪽 끝(θ<−0.35)일 때 33.3%.
  로봇 팔 홈 자세가 top 카메라에서 그 구역을 가리는 것이 원인으로 보인다.
  실기에서도 재현되는지 확인하고, 재현되면 그때 대응한다(각도 범위 축소 또는 해당 구역 집중 수집).
- **실기 배치표의 화각 문제**: sim 박스 각도 ±66°를 그대로 옮겼는데 실기 카메라 화각이 좁아
  큰 각도에서 박스가 프레임 가장자리에 걸렸다. 다음 수집은 **±45°**로 좁힌다.
- **귀속 한계**: 이번 co-training은 sim 데이터(v2→v4_200)와 실기 데이터(real50→real_v2)가
  **동시에** 바뀐다. 선례와의 성능 차이를 어느 쪽에 귀속할지 가릴 수 없다.
  목표가 ablation이 아니라 실기 80% 달성이므로 감수한다.
