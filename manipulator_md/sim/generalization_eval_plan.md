## 1. 공통 원칙 — 측정을 먼저 믿을 수 있게

이 프로젝트에서 **진단이 두 번 뒤집혔고 두 번 다 계측 문제**였다([보고서 §8](README.md)).
같은 실수를 반복하지 않기 위한 규칙이다.

### 1-1. 통제 실험 — 한 번에 한 축만

기준 조건을 고정하고 **한 축만** 바꾼다. 여러 축을 동시에 켜면 신호가 묻힌다
(1차 평가 설계가 이것 때문에 실패했다 — 모든 조건이 45%로 붙었다).

### 1-2. 분모를 먼저 검사한다

- **sim**: 블록이 박스·로봇팔에 가려 파지 불가능한 씬은 **분모에서 제외**한다.
  실측 발생률 **17.8%** — 빼지 않으면 어떤 비교도 무의미하다.
  `scenes.csv`의 `block_box_dist < 0.08`을 1차 후보로 잡고 **영상으로 확인**한다.
- **실기**: 물체가 그리퍼 사거리 밖이거나 박스가 화면 밖인 시행은 제외하고 사유를 기록한다.

### 1-3. 표본 수와 신뢰구간

| N | 95% CI 폭 (SR 70% 기준) |
|---|---|
| 10 | 약 ±25%p |
| 20 | ±19%p |
| **45** | **±13%p** |

**N=10에서 20%p 이내 차이는 노이즈다.** 두 번의 오진단이 모두 N=10~20에서 방향을 확정한 결과였다.

- **sim**: 무인이라 사람 비용이 0 → **조건당 45ep** (약 30분)
- **실기**: 사람이 붙어야 함 → **조건당 10회**, 차이가 애매하면 그 조건만 20회로 늘림

### 1-4. 기록

- sim: `scenes.csv`(좌표) + 영상. 판정은 `analyze_eval_scenes.py`로 구간 분해
- 실기: `LOGDIR`로 시행별 분리 — `video.mp4`, `actions.csv`, `chunks.csv`, rerun 실시간

### 1-5. 성공 판정

sim은 `vial_placed_on_rack` termination을 쓴다(2026-08-06에 `grasp_history_window`
20→1000으로 고쳐 오표기 0건 확인). **단, 물체 형상을 바꾸면 재검증이 필요하다**(§3-4 주의).
실기는 육안 판정한다.

## 2. 평가 A — 실기 진단 (배치표 기반)

> **co-training 완주 직후 가장 먼저.** 다음 학습 레버가 여기서 결정된다.

### 2-1. 설계

실기 데이터는 **박스 자세 10개 × 6ep**로 모았다([배치표](real_collect_schedule.md)).
학습에서 **본 자세**와 **못 본 자세**를 반반 시험해 결핍의 성격을 가른다.

| 조건 | 시행 | 박스 자세 |
|---|---|---|
| **In-dist** | 5회 | 배치표의 자세 **1, 3, 5, 7, 9** 를 그대로 재현 |
| **OOD** | 5회 | 배치표에 **없는** 자세 — 인접 자세의 **중간값** (예: 자세 1과 2 사이 각도·거리) |

블록은 두 조건 모두 근접(8~18cm)과 원거리(20~30cm)를 섞는다.

### 2-2. 판정과 처방

| 결과 | 해석 | 다음 레버 |
|---|---|---|
| **둘 다 실패 / collapse** | 실기 노출 부족 (underfit) | **스텝 ↑ (86k)** — 데이터 추가는 오히려 epoch을 깎아 역효과 |
| **In-dist 성공, OOD 실패** | **커버리지 갭** | 실기 **자세 추가 수집** + 스텝 동반 상향 (57→97ep면 82k 필요) |
| **둘 다 성공** | 문제 없음 | 평가 C로 진행 |
| 파지·접근 자체를 못 함 | **sim 스킬 부족** | 86k 재학습 (sim epoch 18.5 → 33.2) |

> **왜 이 구분이 중요한가**: 데이터를 늘리면 같은 스텝에서 실기 epoch이 **오히려 줄어든다**
> (57ep 40.0 → 97ep 23.5). "노출 부족"인데 데이터를 늘리면 악화된다.

### 2-3. 실행

```bash
# 5090
~/serve_blocktask_n16_5090.sh gr00t_blocktask_cotrain_v4_n16_8bit/checkpoint-48000 start

# 로컬 — 시행마다 LOGDIR을 바꾼다
cd ~/manipulator_ws/setup/gr00t
HOME_SCRIPT=goto_home_real.py \
LOGDIR=~/manipulator_ws/logs/evalA/indist_pose1_t1 \
STEP_DT=0.033 SERVER_HOST=192.168.0.56 ENSEMBLE=1 ENSEMBLE_W=0.3 ./home_then_infer.sh
```

> ⚠️ **`HOME_SCRIPT=goto_home_real.py`** — 실기 데이터가 섞인 모델은 실기 rest 자세로 시작해야 한다.
> zero-shot에서 쓰던 `goto_home_sim.py`와 다르다.

## 3. 평가 B — sim 일반화 (v4_200, sim-only)

> sim은 무인·재현 가능·ground-truth 판정이라 **넓게 훑기 좋다.**
> 여기서 어느 축이 약한지 알아내면, 실기에서는 그 축만 확인하면 된다.

### 3-1. 기준 조건

`full`(수집과 동일한 전체 랜덤) · 45ep · seed 고정. **현 성적 75.6%가 기준선**이다.

### 3-2. 축 1 — 지시문 (언어 일반화)

물체·씬은 그대로 두고 **문장만** 바꾼다. VLM 백본이 언어를 실제로 쓰는지, 아니면
시각만 보고 외운 행동을 내는지 가른다.

| # | 지시문 | 변형 |
|---|---|---|
| L0 | `Pick up the block and place it in the box` | **학습 문장 (기준)** |
| L1 | `Pick up the red block and place it in the box` | 속성 추가 |
| L2 | `Put the block into the box` | 축약·동사 변경 |
| L3 | `Grab the cube and put it in the container` | **동의어 전면 교체** |
| L4 | `Move the red cube into the black container` | 전면 교체 + 속성 |
| L5 | `Pick up the block and place it on the table` | **의미 충돌** (실제 태스크와 다른 목적지) |

- **L1~L4가 L0와 비슷하면** → 언어를 유연하게 해석함
- **L3~L4에서 크게 떨어지면** → 특정 토큰에 과적합
- **L5에서도 박스에 넣으면** → **언어를 안 보고 시각만으로 행동** (중요한 발견)

> L5는 "언어를 정말 쓰는가"를 가르는 대조군이다. 성공률이 높을수록 오히려 **나쁜 신호**다.

### 3-3. 축 2 — 물체 색상

이미 측정된 축이다(`color_blue` 70%, `color_green` 100%, N=10).
**N=45로 재측정**해 신뢰구간을 좁힌다. 추가로 노랑·흰색을 넣어 극단을 본다.

| 조건 | diffuse_color |
|---|---|
| `color_red` (기준) | (0.9, 0.1, 0.1) |
| `color_blue` | (0.1, 0.1, 0.9) |
| `color_green` | (0.15, 0.6, 0.15) |
| `color_yellow` | (0.9, 0.85, 0.1) |
| `color_white` | (0.9, 0.9, 0.9) ← **배경과 유사 → 검출 난이도 최대** |

### 3-4. 축 3 — 물체 형상·크기 (신규)

`block_base.spawn`이 `CuboidCfg`라 교체·조정이 가능하다.

| 조건 | 변경 | 의도 |
|---|---|---|
| `obj_cube` (기준) | 20mm 정육면체 | — |
| `obj_small` | **15mm** 정육면체 | 파지 정밀도 |
| `obj_large` | **28mm** 정육면체 | 그리퍼 개폐 한계 |
| `obj_sphere` | 반지름 10mm 구 | **형상 일반화** |
| `obj_cylinder` | 반지름 10 × 높이 20mm 원기둥 | 형상 일반화 |
| `obj_tall` | 20×20×35mm 직육면체 | 종횡비 |

> **⚠️ 성공 판정 재검증 필요**: 구·원기둥은 놓은 뒤 **굴러서 박스 경계를 벗어날 수 있다.**
> 판정 로직은 "그리퍼가 떨어진 뒤 경계 안"을 보므로 굴러 나가면 실패로 찍힌다.
> 형상 조건은 **영상으로 전수 확인**하고, 오표기가 많으면 그 조건만 육안 판정한다.
>
> 또 그리퍼 접촉 판정(`force_threshold=2`)이 작은 물체에서 안 걸릴 수 있다.
> `obj_small`은 파지했는데 미판정이 나오는지 먼저 5ep로 확인한다.

### 3-5. 축 4 — 씬 외형

| 조건 | 변경 | 비고 |
|---|---|---|
| `box_color` | 박스를 회색·갈색으로 | 현재 검은색 고정 |
| `mat_texture` | 테이블 매트 텍스처 변경 | 배경 일반화 |

> **조명은 제외한다.** `sky_light` 랜덤화가 렌더에 거의 도달하지 않음이 실측 확인됐다
> (라이트박스가 씬을 감쌈, ep별 밝기 175.9/180.3/176.8…로 동일).
> 조명을 정말 바꾸려면 `reset_lightbox_light_exposure` 범위를 건드려야 한다.

### 3-6. 실행

```bash
# 조건별 45ep, 무인. 조건당 약 30분
LANG_INSTRUCTION="Grab the cube and put it in the container" \
MODEL=gr00t_blocktask_v4_200_n16_8bit/checkpoint-86000 \
  ~/blocktask_headless_scenes.sh full 45 31

# 분석
python3 setup/sim/t1_task/analyze_eval_scenes.py --label "L3" \
  --exclude "<겹침 ep>" inf_video/05_genA/hl_full_s31
```

### 3-7. 우선순위 (전부 돌리면 21조건 × 30분 = 10시간)

| 순위 | 조건 | 근거 |
|---|---|---|
| 1 | **L0, L3, L5** (3개) | 언어를 쓰는지 여부가 가장 큰 정보 |
| 2 | `obj_sphere`, `obj_small` (2개) | 형상 일반화의 양 극단 |
| 3 | `color_white` (1개) | 검출 난이도 최대 |
| 4 | 나머지 | 위에서 신호가 보인 축만 채움 |

**1~3순위 6조건 = 3시간**이면 어느 축이 약한지 윤곽이 잡힌다.

## 4. 평가 C — co-train 모델의 실기 일반화

> B에서 찾은 약축이 **실기에서도 재현되는지** 본다. 실기는 시행 비용이 크므로
> **B에서 유의한 차이가 나온 축만** 가져온다.

### 4-1. 조건 (B 결과에 따라 확정)

| 축 | 실기 조건 | 준비물 |
|---|---|---|
| 지시문 | L0 / L3 / L5 | 없음 — `LANG_INSTRUCTION` 환경변수 |
| 물체 | 기준 큐브 / 다른 물체 2종 | **실물 준비 필요** |
| 박스 | In-dist / OOD 자세 | 평가 A와 통합 |

**물체 후보**: 로봇 매니퓰레이션 벤치마크에서 흔히 쓰이는 것으로 고른다 —
YCB 세트류(작은 블록, 주사위, 스펀지 큐브) 또는 크기·색이 다른 큐브.
sim에 없는 물체일수록 일반화 시험이 되지만, **너무 다르면 태스크 자체가 달라진다**
(예: 원통형은 그리퍼 파지 방식이 다름). **크기·색 변형부터** 시작하는 것을 권한다.

### 4-2. 시행 수

조건당 **10회**. B에서 큰 차이(20%p 이상)가 나온 축은 20회로 늘린다.

### 4-3. 실행

```bash
cd ~/manipulator_ws/setup/gr00t
LANG_INSTRUCTION="Grab the cube and put it in the container" \
HOME_SCRIPT=goto_home_real.py \
LOGDIR=~/manipulator_ws/logs/evalC/L3_t1 \
STEP_DT=0.033 SERVER_HOST=192.168.0.56 ENSEMBLE=1 ENSEMBLE_W=0.3 ./home_then_infer.sh
```

## 6. 실행 순서

```
[지금]  co-training 48k 완주 대기                      (약 12h)
   ↓
[1] 평가 A — 실기 진단 10회                            (1h)  ← 최우선, 학습 레버 결정
   ↓
   ├ "둘 다 실패" → 86k 재학습 (65h) 후 A 재실행
   ├ "OOD만 실패" → 실기 수집 + 82k 재학습
   └ "둘 다 성공" → 아래로
   ↓
[2] 구현 (지시문·물체 프리셋)                          (1h)
   ↓
[3] 평가 B — sim 일반화 1~3순위 6조건                  (3h, 무인)
   ↓
[4] 평가 B 결과로 약축 특정 → 필요 조건만 추가          (0~7h)
   ↓
[5] 평가 C — 실기에서 약축 재현 확인                    (2~3h)
```

**평가 B는 co-training과 무관**하므로(대상이 `v4_200`) 5090이 비는 시간에 언제든 돌릴 수 있다.
다만 GPU를 쓰므로 재학습과는 겹칠 수 없다.
