**검증 통과 항목**

- 에피소드당 지시문 **정확히 1개** — 280/280. 예행에서 드러났던 recorder 경쟁 상태가 재발하지 않았다
- 물체별 타깃 균형 29~40 (기대 35 ±30%)
- 미학습 색(흰·분홍) 유출 **0건** — 일반화 평가가 유효하다
- parquet 280개 전부 정상, mp4(external/ego) 280:280:280, 결번·고아 없음

### 수집 중 해결한 문제 셋

**① 마커가 그리퍼에 자석처럼 달라붙음.**
각감쇠를 100 → 5로 낮춰도 그대로였다. 질량·관성을 실측했더니 전부 이론값과 일치했고
(`probe_object_contact.py`), 마찰은 DR이 세 물체에 같은 범위를 덮어쓰고 있었다.
남은 차이는 **충돌 형상 하나**였다 — PhysX 기본 도형은 구·캡슐·박스뿐이라 USD Cylinder만
근사(custom geometry/볼록 껍질) 경로를 탄다. 큐브·지우개는 박스 콜라이더라 멀쩡했다.
→ **마커를 캡슐로 교체**(`radius=0.0065, height=0.057`, 전체 길이 70mm 유지). 해결.

**② 영상 인코딩이 172번째에서 멈춤.**
parquet은 쓰였는데 mp4가 안 나왔다. 저장 자식 프로세스 2개가 7분째 CPU 0%로 잠들어 있었다.
Rerun 뷰어가 5시간 동안 CPU 136%·RAM 19GB를 물고 있었고 코덱은 소프트웨어 AV1이었다.
→ 강제 종료 후 잘린 parquet을 지우고 재개. `blocktask_collect_lang.sh`에 **`RERUN=0` 스위치** 추가.

**③ 잘린 parquet으로 데이터셋이 안 열림.**
`lerobot_recorder.init_dataset()`의 `except:`가 진짜 예외를 삼켜 `folder already exists`로
뭉뚱그려 보고했다. 실제 원인은 강제 종료 때 잘린 `file-NNN.parquet` 하나였다
(`Parquet magic bytes not found in footer`). 그 파일만 지우면 복구된다.

### 도중에 겪은 시스템 장애

**NVIDIA 드라이버 절반 업그레이드로 수집이 2일간 중단.**
9/18 데스크톱 소프트웨어 업데이터(aptdaemon)로 실행한 일괄 업데이트가 dpkg 에러로 중단돼
nvidia 패키지 5개가 `iU`로 남았다. 커널 모듈은 580.178.04인데 `libnvidia-compute-580`만
580.159.03에 머물러 `nvidia-container-cli`가 `driver/library version mismatch`로 죽었다 —
**컨테이너 GPU 접근이 통째로 막혔다.**
되돌리려 했으나 24.04용 580.159.03은 우분투 pool에서 이미 삭제됐고, DKMS 모듈은 커널 -30·-31
양쪽에 178.04로 빌드돼 있어 예전 커널로 부팅해도 같은 불일치였다.
→ `dpkg --configure -a`로 끊긴 설치를 완결. 이후 **nvidia 5종 `apt-mark hold`**.
  수집·학습이 끝나면 풀 것.

## 3. 기준선 프로브 (G1) — **이번 작업의 핵심 측정**

`setup/gr00t/probe_language.py` (신규). 같은 관측(사진 2장 + 관절 상태)을 고정하고
**지시문만 바꿔** 행동 청크가 얼마나 벌어지는지를 °로 잰다. 로봇도 사람도 필요 없다.

현 모델 `gr00t_blocktask_v4_200_n16_8bit/checkpoint-86000`, n=72:

| 비교 | 평균 Δ | 최대 Δ |
|---|---|---|
| 잡음 하한 (같은 문장 2회) | **0.21°** | 1.15° |
| 색 (red ↔ blue) | **0.21°** | 1.17° |
| 이름 (eraser ↔ marker) | **0.21°** | 1.14° |
| 목적지 (black ↔ brown box) | **0.20°** | 1.08° |
| 패러프레이즈 (동의어) | 0.22° | 1.17° |

**다섯 값이 전부 0.20~0.22°로 구별되지 않는다.** 목적지 비교가 같은 문장 2회보다
오히려 낮은 것이 결정적이다 — 지시문을 바꿔 생긴 차이가 **확산 샘플링 잡음보다도 작다**.

참고 눈금: 영상을 좌↔우로 통째 바꾸면 **18.9°**(`probe_swap_images.py` 실측).
프로브가 큰 효과를 못 읽는 도구가 아니라는 증거다.

> **이 측정이 왜 중요한가.** 이것은 "모델이 언어 능력을 잃었는가"의 측정이 아니다.
> GR00T는 언어 인코더를 동결(`tune_llm=False`)한 채 학습하므로 능력은 애초에 망가지지 않는다.
> 재는 것은 **행동 예측부가 지시문을 입력으로 쓰는가**다. 그리고 이 숫자의 쓸모는
> 현 모델에 대한 정보가 아니라 **측정기의 영점**이다 — 여기서 7°가 나왔다면 학습 후의
> 8°는 아무것도 주장하지 못했을 것이다. 0.21°이므로, 학습 후 5°는 잡음의 24배다.

결과는 `probe_language.json`에 누적 기록한다(체크포인트별 곡선이 그대로 쌓인다).

## 4. 학습 (P4) — 진행 중

**[G4a] 이어학습 확인 — 통과**

`--base-model-path`에 로컬 체크포인트를 주는 경로는 조용히 실패할 수 있다(못 읽으면 base에서
시작해 버린다). 10 step 스모크로 초기 loss를 봤다:

| 출발점 | step 10 loss |
|---|---|
| base `nvidia/GR00T-N1.6-3B` (v4_200 학습 때) | **1.1275** |
| `checkpoint-86000` 이어받음 (이번) | **0.1138** |
| (참고) v4_200이 86k에서 수렴한 지점 | 0.0044 |

약 1/10이다. 0.0044보다 높은 것은 정상 — 데이터셋이 새 씬·새 지시문으로 바뀌었다.

**Run A 설정**

```
--base-model-path .../gr00t_blocktask_v4_200_n16_8bit/checkpoint-86000
--max-steps 25000            # 13.5 epoch (118,521 frames ÷ 64)
--save-steps 2000 --save-total-limit 10
--learning-rate 1e-4 --global-batch-size 2 --gradient-accumulation-steps 32
```

v4_200 학습과 다른 곳은 위 두 줄뿐이다. 나머지는 **일부러 그대로** 뒀다 — 한 번에 한 축만 바꾼다.
`save-steps`를 5000 → 2000으로 줄인 것은 언어가 몇 step에서 살아나는지 곡선을 공짜로 얻기 위함이다.

시작 직후: step 10 loss 0.143, step 20 loss 0.1197, GPU 22.7GB/32GB, 사용률 74%.
예상 소요 **약 18시간**(1,333 step/h 실측).

`ckpt_keep.sh watch`를 함께 띄웠다 — `{2k,4k,6k,10k,16k,25k}`를 별도 폴더에 복사한다.
`--save-total-limit 10` 때문에 20k를 넘으면 2k가 지워지는데, 초반 구간이 이번 실험의 핵심 그림이다.

> **체크포인트 용량 정정.** 계획서의 "9.2GB, optimizer 상태 없음"은 틀렸다.
> 실측 **13GB** = 가중치 9.81GB + `optimizer.pt` 3.29GB. 유지 10개 = 130GB.
> 보관본은 프로브에만 쓰므로 `optimizer.pt`를 빼 개당 9.8GB, 6개 = 59GB. 합계 약 190GB.

## 6. 미결 — G4b를 어떻게 볼 것인가

계획은 6k 체크포인트에서 프로브를 돌려 기미가 없으면(<2°) 5시간에서 손절하는 것이었다.

| | 방식 | 득실 |
|---|---|---|
| A | 6k에서 학습을 멈추고 프로브 후 재개 | 손절 가능. 재개 절차가 매끄럽지 않을 위험 |
| B | 25k까지 돌리고 보관본 전체를 한 번에 프로브 | 단순. 손절 기회를 잃음 |

5090에 다른 대기 작업이 없다면 **B가 합리적**이다 — 손절로 아끼는 14시간의 가치가
재개 실패로 19시간을 날릴 위험보다 크지 않다. 6k 시점에 결정한다.

## 9. Run A 결과 — **실패** (2026-09-25)

> ⚠️ **아래 §9·§10의 롤아웃 수치는 무효다.** 성공 판정기가 고장 나 있었다(§11).
> 프로브 수치(§9의 표)는 판정기를 거치지 않아 유효하지만, **프로브 자체가 둔한
> 도구였음이 §11에서 드러났다** — 언어가 붙은 모델에서도 신호를 못 읽었다.

학습은 완주했다(25k step, loss 0.0864 → 0.0076). 그런데 **언어는 붙지 않았다.**

### 프로브 곡선 — 전 구간 잡음 수준

```
체크포인트              잡음     색     이름   목적지   패러프
v4_200@86k (기준선)    0.21   0.21   0.21   0.20   0.22
lang@2000              1.17   1.30   1.29   1.42   1.27
lang@4000              1.08   1.63   1.15   1.05   1.23
lang@6000              1.65   1.85   1.47   1.51   1.40
lang@10000             1.33   1.70   1.11   1.15   1.14
lang@16000             0.75   1.00   0.86   0.93   1.05
lang@25000             0.81   0.91   0.78   0.74   0.45
```

잡음 대비 초과분이 최대 0.55°다. 합격선 5°는커녕 G4b의 2°에도 못 미치고,
곡선이 오르다 만 것이 아니라 **오른 적이 없다**.

### 프로브·파이프라인이 고장 난 것이 아니다 — 같은 모델에서 대조

`lang@25000`, 같은 서버·같은 코드:

| 바꾼 것 | 변화 | 잡음 대비 |
|---|---|---|
| 잡음 (같은 입력 2회) | 0.36° | 1.00배 |
| 영상 교체 | **7.74°** | 21배 |
| state 교체 | **14.63°** | 40배 |
| **지시문 → 빈 문자열** | **0.49°** | **1.33배** |

**지시문을 통째로 지워도 행동이 안 바뀐다.** 같은 경로로 영상과 state는 20~40배
효과를 내므로 서빙 경로 문제가 아니다. 시점별로도 봤다 — 팔이 아직 안 움직인
`frac=0.0`에서도 초과분 +0.13°로, 어느 시점에도 언어 효과가 없다.

학습 경로도 확인했다. `so100_config.py`에 언어 모달리티가 제대로 있다:
`"language": ModalityConfig(modality_keys=["annotation.human.task_description"])`.
**준비 단계는 전부 옳았고, 그런데도 언어가 안 붙었다.**

### 왜 그런가 — loss가 단서다

loss가 0.0076까지 떨어졌다는 것은 **언어 없이도 손실을 줄일 수 있었다**는 뜻이다.
state 효과가 40배로 가장 큰 것과 맞물린다 — 팔이 움직이기 시작하면 궤적 자체가
목표를 드러내므로 대부분의 프레임에서 언어는 불필요하다. 언어가 진짜 필요한 것은
에피소드 맨 앞 몇 프레임뿐이고, 그 몫은 전체 손실에서 작다.

### base 프로브는 돌릴 수 없다

`nvidia/GR00T-N1.6-3B`에 같은 프로브를 대보려 했으나 실패했다:

```
KeyError: 'new_embodiment'
```

base 모델에는 우리 embodiment가 없다. `NEW_EMBODIMENT`는 파인튜닝이 **만드는** 것이고,
행동 예측부(projector + DiT)의 우리 로봇용 경로도 그때 생긴다. 따라서 "base가 언어를
읽는가"는 우리 관측 위에서 정의되지 않는 질문이다.

이것이 Run A와 Run B의 차이를 다시 규정한다 — 둘은 **행동 예측부의 출발 가중치**만
다르다. Run A는 언어를 무시하도록 굳은 v4_200의 헤드에서 출발했고, Run B는 여러
embodiment에 걸쳐 언어 조건화가 사전학습된 base의 헤드에서 출발한다.
그래서 Run B는 의미 있는 별개 실험이다.

## 10. P5 닫힌 루프 평가 — Run A 모델 (2026-09-26)

프로브는 **한 시점의 행동 청크** 차이만 본다. 작은 차이가 롤아웃 내내 누적되면 결국
다른 물체로 갈 수도 있으므로, 끝까지 굴려 **실제로 무엇을 집어 어디에 넣었는지**를 쟀다.

모델 `gr00t_blocktask_lang_n16_8bit/checkpoint-25000`, 10조건 × 30ep, seed 4242, 총 227분.
영상 300개: `inf_video/10_eval_lang/` (610MB).

| # | 지시문이 가리킨 것 | 성공률 |
|---|---|---|
| 1 | **red** cube → black | **15/30 = 50.0%** |
| 2 | **blue** cube → black | 1/30 = 3.3% |
| 3 | **eraser** → black | 0/30 = 0.0% |
| 4 | **marker** → black | 0/30 = 0.0% |
| 5 | yellow → **black** box | 0/30 |
| 6 | yellow → **brown** box | 0/30 |
| 7 | green → gray (합성) | 0/30 |
| 8 | blue (동의어 문형) | 0/30 |
| 9 | 레거시 (기존 패널·기존 문장) | 21/30 = 70.0% |
| 10 | 모호 "the cube" (red로 채점) | 7/30 = 23.3% |

### 판정 — 전부 불합격

| 지표 | 우연 | 합격선 | 실측 | |
|---|---|---|---|---|
| 물체 선택률 (1~4, 120시행) | 25% | ≥45% | **13.3%** | ❌ |
| 목적지 선택률 (5·6, 60시행) | 50% | ≥65% | **0.0%** | ❌ |
| 기존 성능 (조건 9) | — | 기준선 9/10 대비 −2 이내 | 70% (기준선 90%) | 경계 |

### "항상 빨강으로 간다"가 숫자에 정확히 들어맞는다

물체 선택률 13.3%는 **우연(25%)보다 낮다.** 무작위로 고르는 것이 아니라
**한 물체로만 간다**는 뜻이다. 빨간 큐브로만 가고 파지 성공률이 50%라고 가정하면:

```
조건 1(빨강 지시) 50%  +  조건 2·3·4  0%  →  평균 12.5%
실측 13.3%
```

조건 1↔2가 결정적이다. **같은 화면, 같은 배치(같은 seed), 단어 하나만 red→blue.**
50% → 3.3%로 무너진다. 프로브가 1mm라고 말한 것을 행동이 그대로 확인한다.

`block_red`는 이전 태스크에서 86k step 동안 유일한 대상이었다. 그 습관이 남았고,
280ep·13.5 epoch로도 지워지지 않았다.

### 두 가지 단서

**조건 9가 90% → 70%로 떨어졌다.** 계획의 허용치(−2/10 = 70%) 경계에 걸쳐 통과했지만,
**언어는 못 얻고 기존 성능은 20%p 잃었다.** 이 파인튜닝은 순손실이었다.

**조건 1(50%)과 조건 10(23.3%)이 다르다.** 둘은 같은 씬·같은 seed이고 채점 대상도
같은 red_cube이며, 문장만 "the red block" ↔ "the cube"다. 언어를 완전히 무시한다면
같아야 한다. 다만 같은 문장 반복 대조를 두지 않아 확산 샘플링의 분산을 모르므로,
**이 차이가 신호인지 잡음인지 판단할 근거가 없다.** 주장하지 않는다.
확인하려면 조건 1을 다른 seed로 2~3회 반복해 분산을 먼저 재야 한다.

## 11. 판정기 결함 발견과 결과 뒤집힘 (2026-09-26 ~ 09-27)

사용자가 `10_eval_lang` 영상을 보고 **"지시문대로 수행했는데 실패로 찍힌 것이 많다"**고
지적했다. 확인해 보니 성공 판정기에 결함이 둘 있었다.

### 결함 ① 접촉 센서가 빨간 큐브만 필터

```python
filter_prim_paths_expr=["{ENV_REGEX_NS}/Block_Red"]     # 수정 전
```

`vial_placed_on_rack`은 성공 조건 6개를 모두 요구하고, 그중 하나가 "이 물체를 최근에
잡았는가"다. 그 판단을 접촉 센서가 하는데 `contact_per_filter[:, vial_idx]`로 읽는다.
`vials=[_EVAL_TARGET]`은 1개짜리라 `vial_idx=0` → **필터 0번(=빨간 큐브)의 힘**을 읽는다.
타깃이 파랑이든 마커든 상관없이.

→ 파랑·지우개·마커를 완벽히 집어 넣어도 "잡은 적 없음"이 되어 성공이 안 걸렸다.
   **실패 30건이 전부 900스텝 타임아웃**이었던 것이 그 증거다.
→ 필터를 **타깃 하나**로 바꿨다(`_EVAL_TARGET_PRIMPATH`). vials와 순서가 1:1이어야 한다.

### 결함 ② 수직 검사

원본이 시험관을 랙에 꽂는 태스크라 `abs(up_z) > threshold`가 남아 있었다.
마커는 `_LIE_FLAT`으로 눕혀 놓아 로컬 z축이 수평이고 `up_z ≈ 0`이다. 임계값 0.0에 대해
경계값이라 판정이 불안정했다 → **-1.0으로 검사를 껐다.** 큐브·지우개·마커 어디에도
'수직'이라는 개념이 없다.

### 결론 — 안 되는 것은 "굳은 모델을 푸는 것"이었다

**대조군이 결정적이다.** 조건 1과 조건 10은 같은 화면·같은 seed·같은 채점(red_cube)이고
문장만 `"the red block"` ↔ `"the cube"`다.

```
v4_200@86k   23.3% vs 26.7%   차이 −3.4   (언어 무관)
lang@25k     26.7% vs 26.7%   차이  0.0   (언어 무관)
langB@6k     60.0% vs 23.3%   차이 +36.7  ← red 한 단어가 성공률을 2.6배로
```

**base에서 280ep만으로 파인튜닝하면 언어 조건화가 붙는다.** 그것도 3.2 epoch만에,
`lang@25k`의 13.5 epoch보다 4배 적게 배우고 두 배 넘게 잘한다.

무작위 선택으로는 이 숫자가 안 나온다. 4개 중 무작위로 집고 파지 성공률 p면 조건당 p/4다.
47.5%가 나오려면 p가 190%여야 한다. 역산하면 **지시된 물체를 고르는 비율이 약 55~60%**
(우연 25%의 2배 이상)다.

조건 8(동의어 문형)이 조건 2보다 높은 것(53.3% vs 46.7%)도 근거다 — 문장 형식을 외운 게
아니라 뜻을 읽는다.

**왜 Run A는 실패했나.** `v4_200@86k`는 빨간 큐브 하나에 86k step 최적화된 모델이다.
그 편향과 싸우느라 언어를 못 얻고 **기존 성능 27%p를 잃었다**(86.7 → 60.0).
base에서 출발하면 싸울 상대가 없다.

### 목적지는 부분 성공 — 나눠서 말해야 한다

목적지 선택률 30.0%는 합격선 65%에 못 미친다. 다만 이 지표는 **복합**이다 —
노란 큐브를 고르고(q) 그다음 맞는 상자를 골라야 한다(b).
조건 5·6 합이 `q = 0.20 + 0.40 = 0.60`이고, 그중 상자 정답률은 **black 33% / brown 67%**.
갈색으로 2:1 치우쳐 있다.

> **물체 선택은 된다. 목적지 선택은 약하고 편향돼 있다.**

### 배운 것 둘 — 도구에 대한 기록

**판정기를 의심하라.** "실패가 전부 타임아웃"은 로봇이 아니라 판정기를 의심할 신호였다.
조기 종료 실패가 0건이라는 통계가 이미 그 말을 하고 있었는데 읽어내지 못했다.

**프로브는 닫힌 루프를 대신하지 못한다.** `langB@6k` 프로브는 색 2.39°/잡음 1.56°로
신호가 없다고 했지만 롤아웃은 47.5%였다. 프로브는 한 시점의 발산만 보고 900스텝 누적을
못 본다. 게다가 관측을 **수집 데이터셋**(사람이 조작 중인 상태)에서 뽑아 평가 씬의
상태 분포와 다르다. **프로브는 값이 크면 신호가 있다는 증거지만, 작다고 없다는 증거가
못 된다.** 손절 게이트로 쓴 것은 잘못이었다.
