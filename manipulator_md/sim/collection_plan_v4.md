## 1. 원인 — 블록이 박스에 가까우면 실패한다

좌표 보유 57ep(seed7 20 + 헤드리스 37, 겹침 8개 제외) 기준.

| 블록-박스 중심거리 | SR |
|---|---|
| 0.00 ~ 0.12 m | **2/11 = 18.2%** 🔴 |
| 0.12 ~ 0.18 m | 7/14 = 50.0% |
| 0.18 ~ 0.25 m | 11/15 = 73.3% |
| 0.25 m 이상 | **15/17 = 88.2%** ✅ |

**단조 감소.** 가까움/멂(중앙값 0.194m)으로 나누면 **39% vs 83%**.

### 블록 각도는 2차 요인

| | 가까움 | 멂 |
|---|---|---|
| θ < 0 (오른쪽) | **3/12 = 25%** | 7/8 = 88% |
| θ ≥ 0 (정면·왼쪽) | 8/16 = 50% | 17/21 = 81% |

**멀면 각도와 무관하게 80%대**다. 각도는 가까울 때만 추가로 악화시킨다.
θ 5구간 SR도 44.4 → 54.5 → 64.7 → 66.7 → 75.0%로 단조 증가(오른쪽일수록 나쁨).

> 학습 범위가 θ ∈ (−0.7, 1.25)로 비대칭이라 오른쪽 각도 폭이 왼쪽의 절반뿐이다.

## 2. 이게 수집 필터가 만든 구멍임을 **측정으로 확인**

수집 데이터셋에는 물체 좌표가 저장돼 있지 않다. 대신 평가에는 `scenes.csv`로 실제 좌표가
남으므로, **(픽셀 중심 ↔ 실제 좌표) 59쌍으로 영상→평면 변환을 맞추고** 수집 영상에 적용했다.
(`setup/sim/t1_task/analyze_dataset_geometry.py`)

**보정 정확도**: 블록 잔차 **0.74cm**(최대 1.59), 박스 1.02cm, **홀드아웃 0.9~2.5cm**.

| 구간 | 학습 v3 (99ep) | 자연 분포(유효 37ep) |
|---|---|---|
| 0.08 ~ 0.12 m | 4.0% | 13.5% |
| 0.12 ~ 0.18 | 15.2% | 29.7% |
| 0.18 ~ 0.25 | 16.2% | 21.6% |
| 0.25 이상 | 64.6% | 35.1% |
| **근접(<0.18) 합** | **19.2%** | **43.2%** |

**학습 데이터의 근접 구성이 자연 분포의 절반이 안 된다.**
모델이 못 배운 게 아니라 **덜 본 것**이고, 이번엔 진짜 "데이터에 없는 것"이다.

> **모델 선택 기록**: 처음엔 단순 비례 환산(오차 6.8cm) → 호모그래피(8파라미터)를 썼으나
> **잔차 평균 24cm, 최대 1496cm로 발산**했다. 사영 분모 `h6·u+h7·v+1`이 0 근처를 지나면
> 해가 폭발하는데, 색 분할 검출의 이상치가 이를 유발했다.
> → ① 검출을 **최대 연결성분**으로 바꾸고(반사광이 중심을 끌어당기던 문제)
> ② 분모가 없는 **2차 아핀(u, v, 1, u², v², uv)** 으로 교체해 해결했다.
> 카메라가 거의 top-down이라 2차항이 잔여 원근을 충분히 흡수한다.
>
> ⚠️ 이 문서의 이전 판에 있던 "학습 22.2% vs 자연 47.5%"는 **거친 비례 환산 기반**이었다.
> 위 수치가 정확한 값이며, **결론(근접이 약 절반 부족)은 동일**하다.

## 3. 수집 사양

| 항목 | 값 | 근거 |
|---|---|---|
| **블록-박스 중심거리** | **0.08 ~ 0.18 m** | 겹침(<0.08)은 파지 불가라 제외. 0.18 이상은 이미 80%대 |
| **블록 각도 θ** | **음수 구간에 50% 배분** (자연 비율 36%) | 근접+오른쪽이 25%로 최악 |
| 블록 반경 | 학습 범위 0.16~0.34 유지 | r 구간별 SR에 유의한 패턴 없음(73/50/65%) |
| 박스 위치·yaw | **기존 랜덤 그대로** | 박스 변수는 실패와 무관(실패·성공 평균 차 0.003) |
| 물리 DR | 기존 그대로 | 변수 고정 |
| **수집량** | **65 ep** | §4 |

### 수집 실행

**실행 위치: 로컬 5070 Ti** — 리더암(`/dev/ttyLEADER`)이 여기 물려 있다.
5090은 학습·평가 전용이므로 수집은 로컬, 학습은 5090으로 역할이 갈린다.
수집이 끝나면 데이터셋을 5090으로 옮겨 학습한다.

```bash
# 로컬 5070 Ti
./blocktask_collect_near.sh view      # 배치만 육안 확인
./blocktask_collect_near.sh record    # 리더암 teleop 녹화 (S=저장, R=리셋)
RESUME=1 DSNAME=sim_so101_blocktask_v4_near ./blocktask_collect_near.sh record   # 이어쓰기
```

기존 `blocktask_run.sh`는 그대로 두고 **분리**했다(태스크가 다르므로).
실행 전 Near 씬·태스크·리셋 함수 배포를 **매번 확인**한다 — 미배포로 무효 수집을 한 전례가 있다.

**카메라 오프셋 주의**: `blocktask_run.sh`는 `CAM_X=${CAM_X:-0}`로 코드 기본값(0.03/0.02)을
**0으로 덮어쓴다**. 평가 스크립트는 0.03/0.02를 쓰므로 그대로 두면 학습·평가가 어긋난다.
→ `blocktask_collect_near.sh`는 **0.03/0.02로 명시 고정**했다.

> 기존 v3 수집이 어느 값이었는지는 영상으로 검증했다. 평가로 맞춘 변환을 수집 영상에 적용해
> 복원 위치가 알려진 스폰 범위에 들어오는 비율을 보면 v3 96.3% / 잔여 95.2% / 평가 92.5% —
> 수집 쪽이 오히려 높아 **계통 편차 없음**. (영상 정합 방식은 탐색 경계에 붙어 수렴 실패 → 이 검사로 대체)

### 수집 규칙
- 블록이 박스 **벽에 닿거나 겹친 씬만 R로 제외**한다.
- **"붙어 보여서 어렵다"는 이유로 빼지 말 것. 그게 정확히 메우려는 구멍이다.**
- 파지 각도가 안 나오면 **박스 벽을 피해 비스듬히 접근**하는 시연을 일부러 보여줄 것.
  모델이 못 하는 게 그 동작이다.

## 4. 데이터셋 구성 — **200ep (기존 전부를 쓰지 않는다)**

### 4-a. 왜 295ep가 아니라 200ep인가

처음엔 "231ep 전부 + 신규 65 = 295ep"를 제안했으나, **적은 데이터로 분포가 더 잘 맞는다.**

| | 295ep 안 | **200ep 안 (채택)** |
|---|---|---|
| 구성 | 231 + 65 | 100(v3) + 35(선별) + 65(신규) |
| 근접 ep | 116 | **119** |
| **근접 비율** | 39.2% | **59.5%** |
| 원거리 ep | 180 | 81 (v3 현재 80 유지) |
| 학습 시간 | 95h (126k) | **65h (86k)** |

오래된 **원거리** 데이터가 분모만 키운다. 원거리는 이미 83~88%로 잘 되고 데이터 양이
병목인 구간이 아니므로, 넣어봐야 근접 비율만 희석시킨다.

### 4-b. 최종 구성 ✅ 완료 (`sim_so101_blocktask_v4_200`, 82,951 frames)

| 출처 | ep | 근접 | 비고 |
|---|---|---|---|
| `sim_so101_blocktask_v3` (기존 학습셋) | 100 | 19 | 그대로 사용 |
| 잔여에서 **근접 우선 선별** (v3_3 6 + v3_4 29) | 35 | **35** | 거리 0.072~0.164m |
| **신규 타깃 수집** `v4_near_3` | 65 | **55** | 실측 §4-d |
| **합계** | **200** | **109 (54.5%)** | 원거리 91 (v3의 80보다 많음) |

- 선별 목록: `setup/sim/t1_task/selected_35_near.txt` (거리·반경·각도 포함)
- 선별 35개의 θ<0 비율 **49%** — 자연 36%보다 높아 취약 구역이 자연히 보강된다.

### 4-c. 자연 분포(43.2%)를 넘겨 54.5%로 잡는 이유

근접은 **더 어려운 스킬**이라 같은 비율로는 부족하다(hard-example emphasis).
1.26배 오버샘플이면서도 **원거리 ep가 91로 v3의 80보다 많아** 원거리 퇴행 위험이 통제된다.

> 다만 원거리가 **늘지는 않으므로**, 재평가에서 원거리 SR이 80% 아래로 떨어지면
> 그때 원거리를 보강한다(§8 판정 기준에 포함).

## 5. 구현 — 조건부 샘플링이 필요하다

현재 씬은 블록과 박스를 **독립적으로** 뽑는다. 그대로 수집하면 목표 구간(0.08~0.18m)이
자연 발생률 30%라 **60ep를 얻으려고 200ep를 시연**해야 한다. 사람 시간이 비싸므로 코드로 해결한다.

### 문제: 이벤트 순서
```
VialsToRackEventCfg (base)      : reset_block_position   ← 블록이 먼저
VialsToRackEventDRCfg (하위)     : reset_basket_random    ← 박스가 나중
```
"박스 기준으로 블록을 뽑으려면" 순서가 반대다.

### 해법: 두 리셋을 **하나의 term으로 합친다** ✅ 구현 완료

`mdp/resets.py::reset_block_near_box()` —

1. 박스를 기존과 동일하게 샘플링(arc 0.28~0.34, θ ±1.15, yaw ±π)
2. 목표 거리 `d ~ U(0.08, 0.18)`, 방향 `φ ~ U(−π, π)` → 블록 = 박스 + d·(cos φ, sin φ)
3. 블록이 도달 범위(r 0.16~0.34, θ −0.7~1.25) 밖이면 **재추첨**(최대 200회)
4. 시도의 절반까지는 θ 부호를 목표(θ<0 50%)에 맞추고, 그 뒤엔 풀어 거리 조건을 우선

**거리는 균등 추첨**(면적 균등이 아니다). 면적 균등으로 뽑으면 먼 쪽에 쏠려
정작 취약한 근거리가 적어진다.

**시도 횟수 산정**: 1회 수용률 실측 **36.1%**(θ 부호까지 요구하면 14.5%).
64회였을 때 30회 리셋 중 1회 폴백이 발생해 **200회로 상향** → 실패 확률 사실상 0.

씬 설정은 `VialsToRackEventNearCfg(VialsToRackEventDRCfg)`로 분리하고
`reset_block_position = None`, `reset_basket_random = None`, 새 term 추가.
**수집 전용 task**: `Lerobot-So101-Teleop-Vials-To-Rack-Near`
→ 기존 수집/평가 경로는 **건드리지 않는다**.

### 검증 (수집 전 필수) — `verify_near_scene.py`

```bash
# 5090, 컨테이너 안에서 30회 리셋하고 배치 분포만 출력 (~3분)
python verify_near_scene.py --episodes 30
```

확인 항목: 목표대 적중 ≥95% · 도달범위 100% · θ<0 ≈50% · 박스 반경 0.28~0.34.

**실행 결과 (2026-08-06, 30회)** ✅ 통과 — 폴백 0회

```
블록-박스 거리  평균 0.131  범위 0.083~0.176
목표대(0.08~0.18m) 적중   30/30 = 100%
블록이 도달범위 안        30/30 = 100%
θ<0(오른쪽) 비율          16/30 = 53%
박스 반경 0.281~0.340
```

> 지난번 "씬 미배포"로 무효 측정을 한 전례가 있으므로, **수집 시작 전 5090 배포와 값 확인을 반드시** 한다.
> (구현 중 실제로 걸린 함정: `AppLauncher.close()`가 프로세스를 즉시 끝내 **요약 출력이 통째로
> 유실**됐다 — 30회를 다 돌고도 아무것도 안 찍혔다. 요약은 `app.close()` 전에 출력해야 한다.)

## 6. 학습 계획

| 항목 | 값 | 근거 |
|---|---|---|
| 데이터 | **200ep** (v3 100 + 근접선별 35 + 신규 65) | §4 — 원거리를 덜어내 근접 비율을 59.5%로 |
| 방식 | **신규 학습** | resume은 LR 바닥·샘플러 상태·forgetting ([training_plan.md §2](training_plan.md)) |
| 스텝 | **86k** (66.1 epoch 정합) | v3 40k=65.8ep, 200ep를 40k로 돌리면 30.8ep로 **절반** |
| 시간 | 약 65h | v3 실측 1,333 step/h |
| 하이퍼파라미터 | v3와 동일 | 변수를 데이터 하나로 |
| workers | 4 → **8** | v3 학습 중 GPU util 19% |

**⚠️ 귀속 한계**: "데이터 증가"와 "근접 보강"이 동시에 들어가 어느 쪽 효과인지 못 가린다.
목표가 ablation이 아니라 80% 돌파이므로 감수한다. 필요하면 나중에 v3_200(200ep, 같은 분포)을
추가로 학습해 대조군으로 쓸 수 있다 — **ep 수가 200으로 같아 깨끗한 대조**가 된다.

## 7. 실행 순서

```
[1] reset_block_near_box 구현 + Near task 등록          ✅ 완료
[2] 5090 배포 + verify_near_scene.py 30회 분포 검증      (3분)  ← 필수
[3] 타깃 수집 65ep — blocktask_collect_near.sh record   (~1.5h, 로컬)
[3b] 수집 분포 검증 — analyze_dataset_geometry.py       (~5분)
[4] 변환 + v3 100ep + 선별 35ep 병합 → 200ep → 5090 전송 (~40분)
[5] 신규 학습 86k                                      (~65h, 5090)
[6] 무인 평가 full 45ep × 2시드 = 90ep                  (~1h, 사람 불필요)
[7] 합격(≥80%) 시 sim2real
```

[6]이 무인으로 가능해진 건 `grasp_history_window` 결함을 고쳤기 때문이다
(20 → 1000; 45ep 측정에서 오표기 0건 확인).

## 9. 수집 실행 결과 (2026-08-06)

`sim_so101_blocktask_v4_near_3` — **65ep / 28,399 frames / 30fps**, `task_name` 절단 없음.

| 시작 시점 블록-박스 거리 | ep | 비율 |
|---|---|---|
| < 0.08 m | 2 | 3.1% |
| **0.08 ~ 0.12** | **30** | **46.2%** |
| **0.12 ~ 0.18** | **23** | **35.4%** |
| 0.18 ~ 0.25 | 5 | 7.7% |
| ≥ 0.25 | 5 | 7.7% |

- **목표대 적중 53/65 = 81.5%**, 근접(<0.18) **55/65 = 84.6%**
- θ<0(오른쪽) 40% (목표 50%, 자연 36%)

### 목표대를 벗어난 10개의 원인

프레임 0부터 이미 멀었고 박스는 8~45cm 움직였다 → **리셋은 정상 발생**.
즉 리셋 후 S를 누르기 전에 **팔이 블록을 쳐냈다**. teleop은 리셋해도 팔이 홈으로 가지 않고
리더암을 따라가므로, 팔이 스폰 자리에 있으면 블록이 밀린다.

데이터가 망가진 것은 아니고 그 10개가 근접 예제가 아닐 뿐이라 **전부 사용**한다
(시연 자체는 정상임을 육안 확인).

> **자동 성공 판정은 실패했다**: 마지막 프레임으로 판정하려 했으나 팔이 박스 위에 걸쳐 있어
> 검은 박스 검출이 팔·그림자로 튀었다. 65ep 중 13ep는 아예 검출 실패(블록이 박스에 가려짐).
> 시작 프레임은 팔이 물러나 있어 정확하지만(잔차 0.74cm) **끝 프레임엔 이 방법을 쓸 수 없다.**

## 10. 병합·학습 실행 (2026-08-06)

```bash
./prepare_blocktask_v4_200.sh          # 전송 → v3.0→v2.1 변환 → 선별 병합 → 검증
ssh 5090 '~/train_gr00t_blocktask_v4_200_n16_8bit.sh'   # 86k steps
```

**병합 중 잡은 결함 2건**
1. `merge_blocktask_v2.py`는 병합본에 **`modality.json`을 넣지 않고 `stats.count`도 남긴다.**
   세션별 변환 때 한 후처리는 세션 파일에만 적용되므로 병합본엔 따라오지 않는다.
   그대로 학습을 걸면 GR00T가 modality를 못 찾아 실패한다. → prepare 스크립트에 후처리 단계 추가,
   학습 스크립트에도 **선확인 게이트** 추가(한참 뒤에 실패하는 것을 막는다).
2. ssh→docker **heredoc이 인용 단계를 거치며 통째로 유실**돼 검증 출력이 비었다.
   `python -c`로 단순화. (`verify_near_scene.py`의 `app.close()` 출력 유실과 같은 유형)

**세션별 에피소드 선별**은 기존 merge가 지원하지 않아 `merge_blocktask_select.py`를 만들었다.
`file-NNN ↔ episode_NNNNNN` 대응이 어긋나면 선별이 엉뚱한 ep를 고르므로 **채택 개수를 검증**하고
불일치 시 중단한다(6+29=35 정확히 채택 확인).
