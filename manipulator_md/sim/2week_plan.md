→ **R 키로 무효 씬을 빼며 육안 판정**으로 전환.

- `light_dr` 제외: **효과 없음 실측**. 라이트박스가 씬을 감싸 `sky_light`가 렌더에 거의 영향 없고,

### 변경 ⑤ **v2 재측정 포기** (08-06)

→ **v3 vs v3_200**에 집중(둘은 완전히 동일한 씬이라 변수가 데이터 양 하나).

### 변경 ⑥ **육안 GUI → 무인 측정으로 복귀** (08-06 저녁)
성공 판정 결함(`grasp_history_window=20`)을 고치자 자동 라벨이 신뢰 가능해졌다

무인으로 45ep을 30분에 돌릴 수 있게 됐다. → **원인 규명에 필요한 N을 확보**.

### 변경 ⑦ **진단 방향 전환: 언더핏 → 블록-박스 근접** (08-06 저녁) ⭐
`box_rand` 50%(ref 90% 대비 −40%p)를 근거로 "언더핏"이라 진단했으나,
GUI 재측정에서 **70% vs 80%(−10%p)** 로 노이즈 범위였다. **−40%p는 겹침 아티팩트였다.**
좌표를 기록해(`scenes.csv`) 재분석하니 진짜 원인은 **블록-박스 거리**였다.
→ 2차 학습 계획을 "데이터 2배(v3_200)"에서 **"근접 구성 타깃 수집"** 으로 변경.

### 변경 ⑧ **분기 진단(box_pos_only/box_yaw_only) 취소** (08-06 저녁)
분해하려던 −40%p 자체가 아티팩트로 밝혀져 진단의 전제가 사라졌다.
프리셋은 만들어뒀으나 실행하지 않는다.

> 절반이라 오히려 더 언더핏된다. epoch 정합이 86k.

#### 왜 v3@40k에서 이어 학습(resume)하지 않았나

"이미 40k를 돌린 가중치가 있으니 거기서 이어가면 30시간을 아낀다"는 선택지가 있었다.
**쓰지 않았다.** 이유가 네 가지이고, 앞의 둘은 실측·소스 확인으로 뒷받침된다.

**① cosine LR이 40k에서 이미 0으로 완주했다**

학습률은 peak 1e-4에서 cosine으로 감쇠하며 `max_steps`에 맞춰 0에 도달한다.
v3는 40k를 **완주**했으므로 그 지점의 LR이 사실상 0이다.

| step | v3의 40k 스케줄 | 신규 86k 스케줄 |
|---|---|---|
| 10,000 | 8.95e-05 | 9.88e-05 |
| 20,000 | 5.41e-05 | 9.12e-05 |
| 30,000 | 1.61e-05 | 7.75e-05 |
| **39,999** | **1.7e-13** (≈0) | 5.98e-05 |
| 50,000 | (종료) | 4.07e-05 |
| 86,000 | (종료) | 0 |

- LR을 **그대로 두면** 0에서 시작하므로 가중치가 거의 안 움직인다 → 추가 학습이 무의미.
- LR을 **리셋하면** 0 → 5.98e-05로 튀는 **warm restart**가 된다. 성능이 반드시 나빠지는
  것은 아니지만(SGDR 계열은 의도적으로 이렇게 한다), **40k 이전 구간의 LR 이력이
  신규 학습과 완전히 달라** 같은 86k를 돌아도 최적화 궤적이 다른 모델이 나온다.

**② 데이터셋이 바뀌면 샘플러 상태가 어긋난다** (GR00T 고유 위험)

GR00T는 `ShardedMixtureDataset(IterableDataset)`을 쓰고, trainer에
*"stateful samplers rely on global_step"* 이라고 명시돼 있다.
샘플러가 `global_step`으로 자기 위치를 복원하는데, resume 시 **데이터셋 구성이 바뀌면
그 위치가 다른 샤드 레이아웃을 가리킨다.** v3(100ep) → v4_200(200ep)은 에피소드 수가 2배,
샤드 구성이 완전히 다르다. 조용히 어긋나므로 **로그로는 알아채기 어렵다.**

**③ 분포가 크게 바뀌어 catastrophic forgetting 위험이 크다**

이번 변경은 단순 증량이 아니라 **분포 재설계**다.

| | v3 학습셋 | v4_200 |
|---|---|---|
| 근접(<0.18m) 비율 | 19.2% | **54.5%** (2.8배) |
| 원거리 ep | 80 | 91 |

resume은 시간순으로 "**먼저** 원거리 위주 → **나중에** 근접 위주"를 보게 되어
**나중 분포에 편향**된다. 우리가 지키려는 것이 바로 *"근접을 올리되 원거리 83~88%를 유지"*
인데, resume은 그 반대 방향으로 압력을 준다.
신규 학습은 200ep를 **처음부터 섞어** 보므로 양쪽을 균형 있게 배운다.

**④ 변수가 둘이 되어 해석이 막힌다**

이번 학습의 질문은 *"근접 보강이 효과가 있는가"* 하나다. resume을 쓰면 **데이터 분포 +
LR 스케줄** 두 가지가 동시에 바뀌어, 결과가 좋든 나쁘든 원인을 지목할 수 없다.
이미 이 프로젝트에서 진단이 두 번 뒤집혔다(§1 변경 ⑦) — 해석 가능성을 더 깎을 이유가 없다.

#### resume이 적절한 경우 (참고)

**진단**에는 유효하다. 예를 들어 "v3가 언더핏이었나? 더 돌리면 오르나?"를 확인할 때는
같은 데이터로 스텝만 늘려 resume하면 절반 비용으로 방향을 알 수 있다
(데이터가 같으므로 위험 ②③이 없다). 다만 **최종 비교표에 올릴 수치는 신규 학습으로 재생산**한다.
상세: [training_plan.md §2](training_plan.md)(대체된 문서이나 이 절은 유효).

#### 비용

신규 86k ≈ 65시간. resume(46k 추가) ≈ 35시간. **30시간을 더 쓰는 대신
해석 가능한 결과 하나를 얻는 선택**이다. 지금은 원인을 좁혀가는 단계라 이쪽이 맞다.

> **귀속 한계(남는 것)**: 그럼에도 "데이터 증가(100→200ep)"와 "근접 보강(19.2→54.5%)"이
> 동시에 들어가 어느 쪽 효과인지는 못 가린다. 목표가 ablation이 아니라 80% 돌파이므로 감수한다.
> 분리가 필요하면 **v3_200**(같은 200ep, 근접 보강 없음)을 같은 86k로 돌려 대조군으로 쓴다 —
> ep 수가 같아 변수가 '근접 비율' 하나로 깨끗하게 남는다.

### 4-e. 재평가 (무인, 사람 불필요)
```bash
for s in 21 22; do ~/blocktask_headless_scenes.sh full 45 $s; done   # ~1h
```

| 지표 | 목표 | v3@40k |
|---|---|---|
| `full` 전체 | ≥80% | 61.4% |
| **근접(<0.18m)** | **≥70%** | **39%** ← 핵심 |
| 원거리(≥0.18m) | 유지 ≥80% | 83% |
| OOD 평균 | ≥70% | 82.5% ✅ |

원거리가 떨어지면 catastrophic forgetting → 데이터 비율 재조정.

### 4-f. 최종: sim2real
합격(SR≥80% / OOD≥70%) 시 진행. 서빙 스크립트는 **수정 불필요**(모델 경로만 인자로 전달).
```bash
ssh 5090 '~/serve_blocktask_n16_5090.sh gr00t_blocktask_v3_*/checkpoint-40000 start'
# 로컬: goto_home_real.py + ENSEMBLE=1 W=0.3 + real_pose_align 정렬 확인
```
실기는 zero-shot이므로 [report2 §5](../sim2real/08_T1_sim2real/report2.md) 선례대로
**co-training이 추가로 필요할 가능성이 높다**.

## 5. 위험 요소 — 실제 발생분과 대응

| 위험 | 실제 발생 | 대응·교훈 |
|---|---|---|
| Isaac Sim 크래시 | **2회** | `docker rm -f blocktask`로 좀비 정리(VRAM 회수) 후 새 폴더로 재개 → 손실 0 |
| USB(리더암) 분리 | **1회** (2.5h 세션 중) | 저장분 82ep 온전, 재연결 후 재개 |
| 5090 접속 불가 | **1회** | 유선/WiFi 동일 서브넷 충돌 → `ip route replace <5090>/32 dev <wifi>` |
| **씬 미배포** | **1회** | 로컬 fork만 고치고 5090 rsync 누락 → **무효 측정**. sweep에 **씬 버전 검증** 추가로 방어 |
| **잘못된 데이터로 학습** | **1회** | task 문자열 절단 버그, 학습 12분 시점 발견 → 재시작. **수집 후 메타 검증 필수** |
| **측정 영상 유실** | **1회** | 원격 정리 후 로컬 삭제 → 수집 스크립트를 **로컬 확보 검증 후 정리**로 변경 |
| **씬 파일 드리프트** | **1회** | 비정상 종료로 조건이 남은 파일을 다음 실행이 '기준'으로 백업 → `ref` 상태로 영구화. **불변 기준본(`.v3base`)에서만 복원**하도록 변경 |
| **측정 지표 결함** | **1회** | `grasp_history_window=20`으로 성공 판정이 영구 미발생(40ep 중 3ep). 1000으로 수정 후 오표기 0건 |
| **오진단** | **2회** | ① "언더핏"(겹침 아티팩트를 실력 차로 오독) ② "근접 가설 철회"(seed7 20ep에 근접 표본이 없어 반증으로 오독). 둘 다 **표본이 얇을 때 단정**한 것이 원인 |
| 데이터 부족 | 미발생 | 231ep 확보(목표 200 초과) |

**교훈**: 측정 도구를 먼저 신뢰 가능하게 만들었어야 했다. `scenes.csv`(좌표 기록)와
판정 결함 수정이 있었다면 오진단 2회와 GUI 육안 수 시간을 아꼈을 것이다.
