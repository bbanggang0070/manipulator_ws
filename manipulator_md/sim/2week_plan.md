## 1. 계획 변경 이력 — 무엇을 왜 바꿨나

### 변경 ① 색상 다양화 → **위치·박스 랜덤화** (08-04)

| | 원안 | 변경 후 |
|---|---|---|
| 수집 | 큐브 5색 × 50ep = **300ep** | 빨강 고정 + **위치·박스 다양성 100ep** |
| 근거 | (가정) 색이 일반화에 중요 | **실측**: v2에서 색은 강건(파랑 70/초록 90), 위치만 붕괴(10~30%) |

→ 다양성 예산을 **실측된 약점**에 몰아줌. 색 수집은 낭비였을 것.

### 변경 ② 평가 설계: 전체 랜덤 위 측정 → **통제 실험** (08-06)

| | 1차 설계 | 2차 설계 |
|---|---|---|
| 방식 | 모든 조건을 전체 랜덤 위에 얹음 | **기준(ref) 고정 + 한 축만 변경** |
| 결과 | train/pos_ood/box_ood/color **전부 45%** | ref 90% ↔ pos_ood 40% ↔ box_rand 50% |
| 문제 | 베이스 랜덤화가 신호를 덮어 **축 분리 불가** | 축별 기여가 선명하게 분리됨 |

### 변경 ③ 자동 SR → **GUI 육안 판정** (08-06)

자동 sweep 수치를 그대로 못 쓰는 이유 2가지가 확인됨:
1. **success/fail 오표기** — `terminated and not truncated` 기준이라, 눈으로 성공해도
   성공 termination이 안 걸린 채 timeout되면 `fail`
2. **블록-박스 겹침 12.4%** (몬테카를로 20만 회) — 파지 불가능한 씬인데 실패로 집계되어
   **SR을 약 10%p 하향 편향**. 학습 데이터 수집 때는 이런 ep를 수동 제외했으므로 분포 불일치이기도 함

→ **R 키로 무효 씬을 빼며 육안 판정**으로 전환.

### 변경 ④ 측정 조건 9종 → **6종** (08-06)
- `light_dr` 제외: **효과 없음 실측**. 라이트박스가 씬을 감싸 `sky_light`가 렌더에 거의 영향 없고,
  ref와 ep별 밝기가 동일(175.9/180.3/…). 실제 조명 변동은 `reset_lightbox_light_exposure`가
  **모든 조건에 이미** 적용 중.
- `phys_dr` 제외: −20%p로 노이즈 범위. 실기 환경도 조명·물리가 안정적.

### 변경 ⑤ **v2 재측정 포기** (08-06)
v2는 카메라 오프셋 0으로 학습(08-04 18:47에 0.03/0.02로 변경), 박스 고정, 물리 DR 없음,
블록 범위도 다름. 현재 씬으로 재면 **씬 불일치를 재는 것**이라 무의미.
→ **v3 vs v3_200**에 집중(둘은 완전히 동일한 씬이라 변수가 데이터 양 하나).

## 3. 현재 진단 — 언더핏

**`box_rand` 50%가 결정적 증거**. 이건 **학습 때 실제로 겪은 범위**(OOD 아님)인데도 ref 90%에서 반토막.

> 학습 분포 안에서조차 못 한다 = 분포가 좁아서가 아니라 **덜 배운 것**

**원인**: 분포 부피가 폭증했는데 ep 수는 그대로
- 블록 면적 **2.34배** + 박스 위치(**새 차원**) + yaw 2π(**새 차원**) + 물리(**새 차원**)
- 결합 분포로는 **수십 배**, 에피소드는 100 그대로

`full`(50%)과 `box_rand`(50%)가 같은 것도 일관 — **박스 랜덤화가 병목**.

## 4. 향후 계획

### 4-a. 즉시: GUI 육안 측정 6조건 (진행 중)
```bash
xhost +local:root
~/blocktask_gui_cond.sh ref          # / pos_ood / box_rand / box_ood / color_blue / color_green
```
- **R 키**로 겹침 씬 제외, rerun으로 top·wrist 확인
- 결과는 [README §7 체크리스트](README.md)에 기록

### 4-b. 다음: **20분 진단** — yaw vs 위치 분해 ⭐
`box_rand`의 −40%p가 **위치 때문인지 회전 때문인지** 가른다. 30시간 학습의 방향이 여기서 갈린다.

| 조건 | 박스 위치 | 박스 yaw | 해석 |
|---|---|---|---|
| `box_pos_only` | 랜덤 | 고정 0° | 위치만의 효과 |
| `box_yaw_only` | 고정 | 랜덤 ±π | 회전만의 효과 |

- **yaw 병목** → **분포 축소**(yaw ±45°)가 답. 그 차원만 4배 축소되고,
  실기에서 박스가 180° 뒤집힐 일도 없다. **데이터 추가 없이** 개선 가능.
- **위치 병목** → **데이터 2배(v3_200)** 가 답.

### 4-c. 그다음: 2차 학습

| 안 | 데이터 | 학습 | 비용 | 판정 |
|---|---|---|---|---|
| **A1** | 200ep(같은 분포) | 40k 신규 | 30h | **기본안** — 변수 1개 |
| A2 | 200ep | resume | ~15h | 진단용만 |
| B1 | 분포 축소 후 재수집 | 신규 | 2.5h+30h | yaw 병목이면 |
| B2 | 재수집 + resume | | | ❌ 비권장 |

> **resume 위험**(실측 확인): GR00T는 `ShardedMixtureDataset(IterableDataset)`이고
> trainer가 *"stateful samplers rely on global_step"* → **데이터가 바뀌면 샘플러 상태가 어긋난다.**
> cosine LR도 40k에서 0으로 완주해 resume은 **warm restart**. 원인 규명 단계엔 부적합.
>
> **A1의 함정**: 200ep를 40k로 돌리면 **30.8 epoch**(v3의 65.8의 절반) → 더 언더핏될 수 있음.
> epoch 정합은 **86k(66.1 epoch, ~65h)**.
>
> **"취약 축 집중 재수집"은 이미 되어 있음** — 병목(박스 랜덤화)이 v3 데이터에 100% 포함돼 있다.
> 재수집이 의미를 가지려면 **분포를 바꿔야** 한다.

### 4-d. 최종: sim2real
합격(SR≥80% / OOD≥70%) 시 진행. 서빙 스크립트는 **수정 불필요**(모델 경로만 인자로 전달).
```bash
ssh 5090 '~/serve_blocktask_n16_5090.sh gr00t_blocktask_v3_*/checkpoint-40000 start'
# 로컬: goto_home_real.py + ENSEMBLE=1 W=0.3 + real_pose_align 정렬 확인
```
실기는 zero-shot이므로 [report2 §5](../sim2real/08_T1_sim2real/report2.md) 선례대로
**co-training이 추가로 필요할 가능성이 높다**.
